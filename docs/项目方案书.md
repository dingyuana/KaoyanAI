# 项目方案书

> **项目名称：** Kaoyan Wiki（考研智能学习助手）
> **版本：** 1.4.0
> **状态：** 已修订

---

## 一、项目背景

### 1.1 市场痛点

全国硕士研究生入学考试（考研）竞争日益激烈，2027 届报考人数预计持续高位。考生在备考过程中面临三大核心痛点：

| 痛点 | 表现 | 后果 |
|------|------|------|
| **缺乏个性化诊断** | 无法精确知道自己的知识薄弱点，"盲目刷题" | 效率低下，时间浪费 |
| **被动学习** | 教材→听课→刷题的线性流程，缺少动态调整 | 学习计划与实际进度脱节 |
| **信息滞后** | 考研政策、院校招生信息分散，难以及时获取 | 错过关键时间节点 |

### 1.2 AI + 教育趋势

大语言模型（LLM）的快速发展为个性化教育提供了技术基础。国产大模型（通义千问、智谱GLM、MiniMax 等）的成熟，使得构建一个 **AI 驱动的智能学习助手** 成为可行且具有高性价比的方案。

### 1.3 项目起源与思想传承

本项目采用 **Karpathy LLM Wiki** 的核心设计思想：将 LLM 的角色从"事后检索的解释器"转变为"事前编译的知识编译器"，将无序的原始学习资料持续编译为高质量、结构化、自我进化的 Wiki 知识库。在此基础上叠加学习诊断、个性化规划、AI 辅导、错题管理、阶段检测、智能信息中枢等能力，形成覆盖"信息+学习+决策"全周期的智能学习助手系统。

本项目最初定位为"考研数学 Wiki 知识库"（V1/V2），已完成了 PDF 教材→结构化 Wiki 知识库的基础建设。在知识库基座完成后，项目定位升级为完整的智能学习助手系统（V3）。

## 二、项目愿景与目标

### 2.1 愿景

> 打造一个 AI 驱动的考研全周期智能助手，以结构化、可进化的 LLM Wiki 知识库为基座，深度融合备考知识学习与招生信息服务，实现"信息获取 → 学习诊断 → 个性规划 → AI 辅导 → 错题管理 → 阶段检测 → 择校辅助"的全流程闭环，帮助考研学生高效备考、科学决策。

### 2.2 目标

| 维度 | 目标 |
|------|------|
| **知识库** | 以数学二为 MVP 起点，逐步扩散到数学一/三、英语、政治、计算机等专业，遵循"主干+分支"架构 |
| **诊断** | AI 自动出题 + 批改 + 薄弱点归因，客观题批改准确率 ≥95%，薄弱点归因准确率 ≥80% |
| **规划** | 基于诊断结果 + 剩余时间，生成可执行的日/周学习计划 |
| **错题** | 完整闭环（记录→归类→艾宾浩斯复习→同类题推荐） |
| **AI 辅导** | 基于 Wiki 知识库的引导式答疑，避免替学生思考，优秀问答自动沉淀回 Wiki |
| **信息中枢** | 主动采集院校/研究所招生信息及考研政策，基于学生画像推送，编译为结构化 Wiki |
| **择校辅助** | 基于学生学习数据 + 院校报考数据，提供智能择校建议 |
| **阶段检测** | 按学习阶段自动组卷，更新知识状态，支撑计划调整 |
| **扩展** | 中期覆盖数学一/三 + 英语 + 政治，远期扩展计算机等专业课 |

## 三、项目范围

### 3.1 九大核心能力

| # | 能力 | 说明 | 优先级 |
|---|------|------|--------|
| 1 | **知识库基座** | 基于 LLM Wiki 思想，PDF 教材 → 结构化 Wiki 知识库 → 知识图谱 | P0 |
| 2 | **学习诊断** | AI 出题检测学生知识状态，识别薄弱点，归因错误类型 | P0 |
| 3 | **个性规划** | 基于诊断 + 剩余时间生成个性化学习计划，动态调整 | P0 |
| 4 | **错题管理** | 记录、归类、艾宾浩斯复习、同类题推荐 | P0 |
| 5 | **AI 辅导** | 基于 Wiki 知识库的引导式答疑，采用"先提示后解析"模式 | P0 |
| 6 | **智能信息中枢** | 主动采集研招网及各院校招生信息、国家线、调剂政策，编译为结构化 Wiki 并推送 | P0 |
| 7 | **智能择校辅助** | 关联学生能力画像与院校报考难度，提供"保底-稳妥-冲刺"建议 | P1 |
| 8 | **阶段检测与模考** | 按阶段自动组卷，全真模考，输出诊断报告，更新知识状态 | P1 |
| 9 | **能力可视化** | 雷达图/热力图/成长曲线展示知识状态与学习进度 | P1 |

### 3.2 知识库构建策略："主干+分支"架构

为保障 Wiki 知识库的一致性与高质量，采用 **"主干+分支"** 的分层编译架构：

- **主干（知识基线）**：首先选定一套最权威、最系统、最贴合考纲的名师课程（如数学二选用汤家凤或武忠祥老师的体系），对其讲义、视频文稿进行完整编译，生成 `wiki/` 的初始版本，建立标准定义与讲解基线。
- **分支（多视角扩展）**：在主干稳定后，引入其他名师课程（如张宇老师），LLM 在 `AGENTS.md` 规则指引下，只提取与主干有差异的口诀、例题、理解角度，以"补充视角"、"方法对比"等形式轻量接入对应页面，并标注来源。

**知识库的只读性**：终端用户对 Wiki 知识库仅有浏览、搜索、引用权限，不得上传资料触发编译，也不得将个人问答沉淀入知识库。知识库的编译、更新、补充、知识缺口处理均由内容团队通过后台编译流水线统一完成。

### 3.3 知识库的自我进化："知识复利"机制

本项目遵循 LLM Wiki 的"知识复利"理念，让 Wiki 知识库在使用中持续增值：

- 系统自动统计 AI 辅导中的高频未命中知识点，生成"知识缺口列表"，提交内容团队审核。
- 内容团队审核后，通过后台编译流水线将补充内容更新至 Wiki 知识库，所有用户即时可见。
- 终端用户无法触发任何入库操作，知识库写入权完全归属内容团队。
- 伴随大纲每年更新，系统自动识别变更并更新 Wiki 页面，保持时效性。

### 3.4 科目覆盖策略

| 阶段 | 科目 | 说明 |
|------|------|------|
| 初期（MVP） | 数学二 | 高等数学 + 线性代数 |
| 中期 | 数学一/三 | 扩展概率论等 |
| 中期 | 英语 | 阅读/作文/词汇 |
| 中期 | 政治 | 时政/马原/史纲 |
| 远期 | 计算机等专业课 | 408 计算机学科专业基础综合等 |

### 3.5 智能信息中枢范围

| 功能 | 说明 | 优先级 |
|------|------|--------|
| 研招网政策采集 | 国家线、报名流程、考试时间、最新公告 | P0 |
| 院校招生信息采集 | 招生简章、专业目录、复试分数线、录取数据 | P0 |
| 个性化推送 | 基于学生目标院校/专业画像，关键节点主动推送 | P0 |
| 差异对照 | 自动对比今年与去年简章差异，标记风险变化 | P1 |
| 信息编译入库 | 将招生信息编译为结构化 Wiki 页面，与备考知识库双向链接 | P1 |

## 四、目标用户

### 4.1 用户画像

| 属性 | 描述 |
|------|------|
| **身份** | 备考全国硕士研究生入学考试的学生 |
| **年级** | 大三/大四（2027 届为主） |
| **科目** | 初期聚焦数学二考生 |
| **技术背景** | 普通学生，非技术用户 |
| **核心需求** | 高效备考、精准诊断、个性化规划、招生信息获取、择校决策支持 |

### 4.2 用户场景

- **信息获取**：查政策 → 查院校 → 查分数线 → 接收个性化推送
- **入学场景**：首次使用 → 完成 AI 诊断 → 获取学习计划
- **日常学习**：每日任务 → 学习 → AI 辅导答疑 → 记录错题 → 复习
- **阶段检测**：周测/月测 → 知识状态更新 → 计划调整
- **择校决策**：查看能力画像 → 获取院校推荐 → 制定报考策略

## 五、项目组织

### 5.1 三角色治理（CONSTITUTION.md 定义）

| 角色 | 身份 | 职责 |
|------|------|------|
| **CEO** | 用户 / 需求方 | 定义功能需求、审批计划、验收产出、提供领域知识 |
| **Hermes** | 项目管理者 | 制定规范、分解任务、审查代码质量、把控知识质量 |
| **OpenCode** | 执行引擎 | 依据规范实现代码、构建知识库、提交 PR |

### 5.2 协作铁律

- Hermes 是规范的唯一制定者，OpenCode 不得修改规范文件
- OpenCode 禁止直接推送 `main` / `develop` 分支
- 当 CEO 与 OpenCode 分歧时，由 Hermes 裁决

### 5.3 知识库维护规范：AGENTS.md

除项目宪法 `CONSTITUTION.md` 外，项目将维护一份专用的 `AGENTS.md`（注意带"S"）文件，作为 LLM 编译与更新 Wiki 知识库的"指令手册"。它规定了：

- 每个知识点页面的标准结构（定义、公式、名师精讲、例题、易错点等）
- 交叉引用的链接规范与格式
- "分支"课程内容接入主干时的规则
- 大纲更新时的修订与冲突处理策略
- 知识复利内容的入库标准（仅限后台触发）
- AI 辅导的引导式回答规范（先提示，后解析，避免直接给出完整答案）
- **用户权限边界**：明确 Wiki 知识库的读写分离——用户只读，内容团队及 LLM Agent（在管理后台触发）负责写入和维护

该文件由 Hermes 与内容团队共同维护，确保 AI 生成的 Wiki 保持长期的一致性和专业性。

## 八、风险与应对

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| Wiki 内容方向偏差（概率论占比过高） | 高 | 优先补充线代+高数，概率论降级为参考 |
| 学生过度依赖 AI，影响自主思考能力 | 高 | AI 辅导采用引导式设计，默认展示思考路径，不直接给答案；AGENTS.md 明确规范 |
| LLM 生成内容质量不可控 | 中 | 草稿→人工审核，所有变更进 log.md，严格遵循 AGENTS.md 规范 |
| 学生数据混入认知层 | 中 | 代码规范强制物理分离，Code Review 把控 |
| LLM API 服务不稳定 | 中 | 多 Provider Failover 机制 |
| 项目时间紧张 | 中 | P0 优先，P1/P2 弹性排期 |
| 分支课程与主干冲突 | 中 | 严格遵循 AGENTS.md 中的冲突处理规则，创建"方法对比"页面而非修改主干定义 |
| 多科目扩展资源不足 | 中 | 采用模板化 Wiki 页面结构，降低每科边际成本 |
| 招生信息采集的法律合规风险 | 中 | 仅采集公开可访问的信息，遵守 robots.txt，标注信息来源，不做二次售卖 |
| 终端用户误用知识库写入功能 | 低 | 系统架构层面关闭用户写入接口，仅开放只读权限 |
